# Project Memory 新建与迁移指南

[English](workflows.md)

这份指南面向项目负责人和普通使用者，说明什么时候应初始化新项目，什么时候必须先审计再迁移。Agent 的强制执行协议位于 Skill 包内；本指南解释你会看到什么、需要决定什么，以及怎样验收结果。

## 先选择正确路径

| 项目现状 | 使用路径 | 写入规则 |
|---|---|---|
| 新目录，或长期项目但没有任何成体系的项目记忆 | 初始化 | Agent 先只读预检；确认确实是新项目且根目录明确后，可执行用户明确要求的最小初始化。 |
| 已有需求、计划、ADR、交接、经验、`AGENTS.md` 或 `CLAUDE.md` 中的同类 Project Memory 规则，或旧版 Project Memory | 存量迁移 | 必须先完成零写入审计，展示文件级方案，得到用户对具体范围的批准后才能写入。 |
| 无法确定已有文档是否承担项目记忆角色 | 存量迁移 | 按更保守的迁移路径处理；不以文件名猜测角色。 |

安装或更新 Skill 不会自动修改任何项目。每个存量项目都要独立审计和批准。

## 人的职责与 Agent 的职责

项目负责人需要：

- 明确目标项目根目录；
- 决定真正影响范围、规范、权威来源或兼容性的事项；
- 审阅迁移方案中的文件、动作、风险和恢复依据；
- 按项批准、修改、拒绝或延后迁移；
- 查看最终 diff 和验证结果，并决定是否修复或回滚失败项。

Agent 必须：

- 在任何写入前识别项目根目录、现有文档、入口文件和路径边界；
- 按内容和引用关系判断 canonical 文档，不按文件名武断归类；
- 保留已有内容和惯例，不为了套模板而创建竞争副本；
- 把已验证事实、用户决定、假设和待确认事项区分开；
- 只执行当前用户明确授权的项目内动作；
- 在迁移审计阶段保持零写入；
- 只应用已批准的文件级变更，并在结束时报告实际 diff、验证和回滚方式。

## 路径 A：创建新项目记忆

### 1. 发起初始化

推荐提示词：

```text
使用 Project Memory 为当前目录初始化长期项目记忆。先做只读预检；如果发现已有项目记忆、需求、ADR、交接或同类入口规则，请切换为存量迁移审计并停止写入。若确认是新项目，只创建有真实内容的最小结构，并在最后报告 diff 和验证结果。
```

这条指令授权的是当前项目内的最小初始化，不授权扫描其他项目、安装或更新 Skill、提交 Git、push、发布或执行外部操作。

### 2. Agent 先做只读预检

预检至少确认：

- 规范化后的项目根目录和仓库根目录；
- Codex、Claude Code 或双宿主入口；
- 是否已有 `.planning/`、需求、路线图、ADR、状态、经验或同类入口规则；
- 是否存在越界符号链接、并发写入或不明确的 canonical 文档；
- 项目主要文档语言。

如果发现已有同类资料，Agent 不得继续按“空项目”写入，而应转入下面的存量迁移审计。

### 3. 只建立最小可用结构

默认只创建：

- `.planning/context.md`：稳定目标、约束、高层状态、真实文档索引和 schema；
- `.planning/release-log.md`：倒序记录有意义的变化；
- 适用宿主的一个简短受管入口块，且必须最后写入。

`state.md`、回顾、术语、决策、经验、模板和专题文件都应按实际需要延迟创建，不生成空壳文件。

### 4. 人只决定实质问题

根目录、宿主、现有规范或范围存在实质歧义时，Agent 应给出推荐与影响后询问。对于清晰、可逆、已明确要求的新项目初始化，不需要额外的仪式性批准。

### 5. 验收初始化

确认：

- 只创建了有实际内容的文件；
- 已有项目资料没有被覆盖；
- `AGENTS.md` 与 `CLAUDE.md` 在双宿主项目中指向同一份记忆；
- 索引只列出真实存在的文件；
- 验证器通过，最终 diff 与报告一致；
- Agent 说明了下次如何恢复项目工作。

## 路径 B：迁移存量项目

迁移固定分为四个阶段。阶段 1 和阶段 2 都是只读的；没有明确批准，不得进入阶段 3。

### 阶段 1：只读审计

推荐提示词：

```text
使用 Project Memory 对当前项目做迁移前审计。整个审计阶段不得创建、修改、删除、移动或重命名任何文件。请给出审计根目录、基线、schema 分类、canonical 角色映射、冲突与过期内容、危险路径、最小迁移项、恢复依据和验证方案；然后停下来等我逐项决定。
```

审计报告应包含：

- 审计根目录、时间和可识别的 Git/文件基线；
- 方案 ID 与 revision，避免一次批准被套用到后来改变的方案；
- 当前分类：`schema 1`、`legacy managed`、`partial`、`foreign convention` 或 `ambiguous`；
- 路径、实际角色、证据、新鲜度、现有所有者/惯例和冲突；
- 越界符号链接、并发写入和无法确认的权威来源；
- 编号迁移项，例如 `MIG-01`、`MIG-02`；
- 每项的目标文件、最小动作、保留内容、风险和预计 diff；
- 恢复依据和迁移后验证方案；
- 明确声明“审计完成，写入为零”。

审计报告应留在对话中；不能为了保存审计报告而先写入项目。

### 阶段 2：人逐项决定

批准必须指向当前审计中的具体迁移项。示例：

```text
批准 PM-MIG-2026-08-24 方案 revision 1 中的 MIG-01 和 MIG-03 按原方案执行；MIG-02 不执行。除此之外不要修改任何文件。
```

需要修改方案时：

```text
对于 PM-MIG-2026-08-24 revision 1，MIG-01 批准；MIG-02 修改为保留 docs/adr/ 作为 canonical 路径，不创建 .planning/decisions/；请给出新 revision，并再次等待我确认修改项。
```

沉默、继续聊天、安装过新版 Skill、泛泛说“用一下 Project Memory”或“升级项目”都不构成迁移批准。涉及删除、移动、项目外路径、Git 提交、push、发布或全局安装时，还需要对应动作的单独授权。

修改后的迁移项会回到待批准状态。只有全部依赖和不可拆分执行组成员都得到批准，并且这个子集仍能留下结构有效的项目时，部分批准才可执行；否则 Agent 必须保持零写入，并说明还需要哪项决定。如果执行前基线发生变化，受影响的迁移项失效；Agent 必须重新读取并重新展示方案。

### 阶段 3：执行已批准迁移

Agent 只能执行批准表格中的文件和动作，并应：

1. 写入前重新读取每个目标文件；
2. 核验已有的只读基线，并为每个批准项准备文件级反向变更；除非备份或 Git commit 本身被列为独立项并单独批准，否则不得创建；
3. 以最小 diff 补齐 canonical 记录；
4. 保留来源和独有历史，把无法归因的内容标记为 `待确认`；
5. 更新真实索引，并让 release log 准确反映当前状态，不在验证前宣称完成；
6. 在被引用文件都存在后，最后写受管入口块；
7. 重新读取所有变更文件。

迁移不得顺手格式化、重命名或清理未批准的文件。

### 阶段 4：验证与回滚

Agent 应运行只读验证器并检查实际 diff，至少确认：

- 所有路径和符号链接都留在项目根目录内；
- context schema 与入口 marker schema 一致；
- 索引和 Markdown 链接有效；
- ID 唯一，活跃交接状态包含精确下一步；
- 原有独特内容和并发改动仍存在；
- 第二次按同一方案试运行不会再产生 diff；
- 实际改动没有超出批准项。

一旦写入或验证失败，Agent 应停止后续修改，列出成功、失败和未尝试项，并给出文件级修复或反向补丁。回滚也需要在会改动文件时获得批准；不得使用可能抹掉迁移后新工作的大范围 reset 或整体恢复。

只有结构验证通过后，已批准的 release-log 项才能标为完成；随后还要再次运行验证并检查最终 diff。

## 更新旧版 Project Memory 项目

先更新插件或独立 Skill，再对每个项目分别执行存量迁移流程。版本更新本身不代表项目 schema 必须变化；只有 schema 变化或用户选择的项目改进才需要迁移。

不要直接复制新版 `.planning/` 覆盖旧目录。旧项目已有的 `CONTEXT.md`、`STATE.md`、`docs/adr/`、变更日志或经验库可能继续作为 canonical 路径，只需由新协议索引和约束。

## Codex 与 Claude Code

两种宿主共享同一套项目记忆：

- Codex 使用适用层级的 `AGENTS.md`；
- Claude Code 使用适用层级的 `CLAUDE.md`；
- 双宿主项目的两个入口都指向同一份 `.planning/context.md`；
- 不把完整项目记忆复制进两个入口文件。

## 完成标准

一次工作只有在以下条件满足后才算完成：

- 操作路径分类正确；
- 存量迁移有可证明的零写入审计阶段；
- 每个实际变更都能对应到明确初始化授权或批准的迁移项；
- 已有内容、canonical 惯例和并发改动被保留；
- 验证器与项目特定检查通过，或失败被准确报告；
- 最终报告列出根目录、改动文件、保留映射、验证证据、恢复方式和最高优先级待决定事项。
